# Security review, October 2026

A read-only, code-level review of the platform, done by reading the code and running small proofs. It is **not** a
penetration test: nothing was attacked dynamically, and the findings below say how sure each one is.

- **Reviewed at:** `main` after commit `c8226e1` (billing, production ops, DSAR/retention and digests included).
- **Changed by this review:** nothing in the source. Only this file was added.
- **Result:** 0 Critical, 0 High, 3 Medium, 8 Low, 4 Info.

## Method

1. **Route inventory.** `apps/api/src/openapi/inventory.ts` reads Express's own routing table. It lists 292 operations:
   255 behind a session (`authenticateJWT`), 7 behind a SCIM token, 1 with an optional session (`logout`) and 29 with
   no authentication. Every one of the 29 public routes was reviewed by name (see "Public routes").
2. **Targeted reading** of everything added since the last review: the billing and Razorpay webhook, support access,
   offboarding export and deletion, `/ready` and `/metrics`, DSAR and retention, digest unsubscribe, the TLS "ask"
   route, tenant routing.
3. **Whole-repo passes** for: SQL injection (every `$queryRaw`), SSRF (every outbound `fetch`), zip-slip and storage
   keys, upload handling, XSS (e-mail HTML, `dangerouslySetInnerHTML`), CSRF and CORS, open redirects, rate limits,
   JWT handling, secrets in logs and audit, timing-safe comparisons, mass assignment, Docker, Caddy and CI.
4. **Runnable proofs** (throwaway scripts outside the repo, in the session scratchpad) for the redirect and SSRF
   findings. They exercise the same predicates and the platform's URL parser, not the running application.
5. `npm audit --omit=dev` (report only): **0 vulnerabilities** at every severity.

Confidence labels: **Confirmed** = the failing behaviour was reproduced with a script; **Code-read** = the code path was
read in full but not run; **Unverified** = a plausible concern that needs dynamic testing.

### SEC-01 (Medium): open redirect after sign-in

The login page follows `?next=` when it "starts with `/` and not `//`". Browsers and the WHATWG URL parser also treat a
backslash as a slash, and strip tabs and newlines, so these pass the check and resolve to another site:

```
/\evil.com        -> https://evil.com/
/<TAB>/evil.com   -> https://evil.com/     (?next=/%09/evil.com)
/<LF>/evil.com    -> https://evil.com/
```

**Scenario.** A phishing e-mail links to `https://school.lms.example/login?next=/%09/evil.com`. The person signs in on
the real site and is sent to a look-alike page that says "session expired, enter your password again".
**Fix.** Resolve the value against the origin and compare: `const u = new URL(next, location.origin); ok = u.origin ===
location.origin`, then push `u.pathname + u.search + u.hash`. Put it in one helper and use it everywhere `next` is read.
**Not verified:** whether Next's `router.push` hard-navigates for an off-site URL (it normally does).

### SEC-02 (Medium): SSRF guard can be bypassed

`assertSafeWebhookUrl` (also used for OIDC discovery and the SAML entry point) blocks literal private IPv4 ranges, `::1`,
`fc`/`fd`/`fe80` and a few host names. Verified with the production branch of the predicate:

| URL                                                                                                  | Result                         |
| ---------------------------------------------------------------------------------------------------- | ------------------------------ |
| `https://[::ffff:127.0.0.1]/`, `https://[::ffff:169.254.169.254]/`                                   | **allowed** (IPv4-mapped IPv6) |
| `https://[::]/`                                                                                      | **allowed**                    |
| `https://100.64.0.1/` (carrier-grade NAT range)                                                      | **allowed**                    |
| `https://169.254.169.254.nip.io/`, `https://localtest.me/` (names that resolve to private addresses) | **allowed**                    |
| `https://127.0.0.1/`, `https://[::1]/`, `https://2130706433/`, `https://0x7f.1/`                     | blocked                        |

**Scenario.** An organisation administrator with the webhooks feature registers one of those URLs. The API then POSTs a
signed JSON body to an internal HTTPS service, and `POST /admin/webhooks/:id/test` returns the status code or the network
error text, which maps open ports and live hosts. Production requires `https`, which limits what can be reached (the cloud
metadata service is plain HTTP), and the response body is never returned.
**Fix.** Resolve the host name and check every resulting address (including mapped IPv6, `::`, `100.64.0.0/10`, `192.0.0.0/24`,
`198.18.0.0/15`, multicast and reserved ranges) in one function; connect to the checked address (or use an egress proxy
that does this) so a second DNS answer cannot change it. Re-check on each delivery, not only when the URL is saved.

### SEC-03 (Medium): LTI launch can be replayed

`POST /api/v1/lti/launch` signs the person in from an `id_token` alone. The token's signature, issuer and audience are
verified, but the `nonce` is only checked to exist: it is never stored or consumed, there is no `state`, and `exp` is
enforced only if the token carries one (`jwt.verify` does not require it). A captured launch token can be replayed for
as long as it is valid and signs in as that person, including administrators, because the account is matched by e-mail.
**Scenario.** A launch token leaks from a proxy log, a browser history or a support ticket; it is replayed from another browser.
**Fix.** Require `exp` and `iat`, reject tokens older than a few minutes, and store each `nonce` (with the deployment) until
it expires, refusing a second use. Also validate the OIDC third-party login initiation (`state`) if the platform sends it.

### SEC-04 (Low): Razorpay webhook replay protection relies on an unsigned header

The signature covers the body, but the idempotency key is the `X-Razorpay-Event-Id` header, which is not signed. Anyone
who captures a valid signed body can resend it with a new event id and it is processed again (there is also no check on the
event's age). The effect is limited: a repeated `charged` event is harmless (invoices are deduplicated by payment id), but
a replayed `subscription.halted` or `pending` for the organisation's _current_ subscription would mark it past due.
Capturing a signed body needs access to Razorpay's traffic or the API's logs.
**Fix.** Derive the key from the signed body (the payload's own ids and `created_at`), ignore events older than a day, and
never trust the header for deduplication.

### SEC-05 (Low): a read-only support pass is "no changes", not "no data"

The server refuses every non-GET request in a read-only support session, which is sound. The session is a `TENANT_ADMIN`,
so every administrator GET still works, including downloading a finished full-data export
(`GET /admin/offboarding/export/:id/download`). The organisation grants this knowingly, but the pass wording ("read-only")
suggests less. **Fix.** Either deny export downloads and other bulk-data GETs in support sessions, or say so on the pass
screen. Also note one shared support user per organisation: revoking one operator's pass signs every operator out.

### SEC-06 (Low): no re-authentication for destructive administrator actions

Scheduling the organisation's deletion, queuing a full export, cancelling a subscription and changing SSO need only a valid
session. A stolen session (see SEC-03) can do all of them. Deletion has a 30-day grace period, which is a good mitigation.
**Fix.** Ask for the password (or a fresh MFA code) for these actions.

### SEC-07 (Low): the API sends HSTS `preload`; the proxy policy says not to

`server.ts` sends `max-age=31536000; includeSubDomains; preload` on the platform's own hosts. `deploy/Caddyfile` says not to
preload ("hard to undo") and uses `?` so the API's header wins. Preloading is a one-way door, so the two should agree.
**Fix.** Drop `preload` from the API header until the domain is final.

### SEC-08 (Low): no content security policy on the web app

Caddy sends only `frame-ancestors`. The API's policy allows inline scripts, which is moot for a JSON API but means there is
no second line of defence if a cross-site scripting bug appears in the web app. No such bug was found (no raw HTML is rendered
anywhere in `apps/web`). **Fix.** Add a nonce-based CSP in Next.js.

### SEC-09 (Low): rate limits fail open

Every limiter uses `passOnStoreError: true`, and without `REDIS_URL` the counters are per process. A Redis outage (or running two
API replicas without Redis) weakens the login and token-flow limits. Account lockout still applies to password guessing.
`/ready` now reports a Redis failure, which helps. **Fix.** Alert on it and, for login, fail closed or keep a small local
fallback limit.

### SEC-10 (Low): webhook signing secrets are stored in clear

`WebhookEndpoint.secret` is plaintext in the database (SSO client secrets are encrypted with `encryptSecret`). It is only
returned once at creation, but a database dump exposes it. **Fix.** Encrypt it the same way.

### SEC-11 (Low): CI supply chain

GitHub Actions are pinned by version tag, not commit hash, and CI runs no dependency, secret or container scan.
**Fix.** Pin by hash (Dependabot can maintain them) and add `npm audit --omit=dev`, a secret scanner and an image scan.

### Info

- **SEC-12.** SSO, SAML and LTI sign-ins skip the local MFA step (the identity provider is trusted to do it), and an LTI
  launch maps to any account in the organisation by e-mail, administrators included.
- **SEC-13.** CSRF protection is `SameSite=Lax` plus JSON-only bodies (`express.json`), with `__Host-` cookies in production.
  There is no token. That is sufficient today; a new endpoint that accepts form posts or changes state on GET would break it.
- **SEC-14.** The digest unsubscribe token never expires and is keyed from `JWT_SECRET`; rotating the secret invalidates old
  e-mail links. It can only turn digests off.
- **SEC-15.** A fulfilled DSAR access export stays downloadable by the requester indefinitely (it is rebuilt each time).

## Checked and found sound

- **Authentication on every route:** all 255 session routes sit behind `authenticateJWT`; JWTs are HS256 with the algorithm
  pinned, 8 h default lifetime, revocable through `tokenVersion`; the cookie is `httpOnly`, `SameSite=Lax`, `__Host-` in production.
- **Tenant isolation:** the tenant comes from the verified token, never the request; row-level security is forced, and the
  production API connects as the unprivileged `lms_app` role. Every id taken from a request that was sampled (files, quiz
  submissions, DSAR export, offboarding download, support, billing) is re-scoped to the caller's tenant and, where relevant,
  the owner or course staff.
- **SQL injection:** all 11 `$queryRaw` uses are tagged templates with bound parameters; no `$queryRawUnsafe`.
- **Webhooks and callbacks:** the Razorpay, plagiarism-provider and LiveKit signatures use constant-time comparison; the plagiarism
  callback also enforces a timestamp skew; the TLS ask route and metrics use constant-time secret checks and are off when unset.
- **Uploads and files:** content-type allowlist, `nosniff`, sandboxing CSP on inline files, size limits, virus scan hook,
  storage keys validated against a strict pattern (no path traversal).
- **SCORM unpacking:** entry names are validated (no `..`, absolute, backslash or control characters), entry sizes are
  validated, and file count and total size are capped (5,000 files, 200 MB per file, 1 GB total).
- **E-mail:** the digest escapes every interpolated value and only emits `https:` or same-site links; reset and
  verification links are built from the organisation's stored address, not the `Host` header.
- **Mass assignment:** zod strips unknown keys, so `data: body` writes only declared fields; sensitive fields are not declared.
- **Secrets in logs and audit:** the logger redacts authorization, cookie and token paths; the audit sanitiser masks keys that
  contain password, secret or token.
- **Operator and support flows:** the support hand-off link is single-use (atomic claim), short-lived, stored hashed and
  bound to the organisation's own address; every support write is audited.
- **Containers:** API and web images run as `node`; databases, Redis and ClamAV have no published ports; Prometheus is bound to
  loopback; `no-new-privileges` is set on the application services; `/metrics` is not routed by Caddy.
- **Dependencies:** `npm audit --omit=dev` found none.

## Not assessed (needs dynamic testing)

- DNS-rebinding and redirect behaviour of outbound requests at runtime, and the Next.js handling in SEC-01.
- Row-level security as `lms_app` across all 255 session routes: the test suite covers the main paths, but this review
  sampled object-level checks rather than reading all of them.
- Race conditions and business-logic abuse (grading, enrolment, seat limits, invoice numbering under load).
- Denial of service: request-size, zip-bomb and regular-expression behaviour under real load; Caddy's on-demand certificate limits.
- Real deployments: TLS configuration, the S3 bucket policy, the Cloudflare token scope, LiveKit, SMTP, backups' encryption at rest.
- Secrets in git history, base-image CVEs and transitive dependencies inside the built images.
- The DPDP consent code that was still being written when this review ran (not committed).

## Suggested scope for an external penetration test

1. **Tenant isolation:** with two organisations, try to read or change the other's data through every object id, the support
   and operator paths, exports, and the public routes.
2. **Authentication:** login, lockout and rate limits, password reset, MFA, SSO, SAML and LTI (replay, tampering), session
   revocation after suspension and role change.
3. **Outbound requests:** webhook, OIDC, SAML and Copyleaks URLs (SSRF, DNS rebinding, redirects) from a tenant-administrator account.
4. **Files and SCORM:** hostile uploads and packages (zip-slip, bombs, script content, content-type confusion), the content origin boundary.
5. **Billing:** webhook forgery and replay, plan and seat manipulation, invoice access across organisations.
6. **Platform:** custom domains and on-demand TLS, host-header handling, the operator console, support access, offboarding export and deletion.
7. **Web app:** cross-site scripting, open redirects, clickjacking, CSP, client-side storage.
8. **Infrastructure:** the production compose stack, Caddy, exposed ports, container escape, backup and restore handling.
